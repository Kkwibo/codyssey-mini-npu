# Mini NPU Simulator

Codyssey 1-3 과제 「AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기」 결과물입니다.

사람은 그림을 보는 순간 십자가인지 X인지 알아보지만, 컴퓨터는 0과 1 같은 숫자 배열로만 그림을 이해합니다. 그래서 "이 숫자 그림이 십자가 필터와 X 필터 중 어디에 더 가까운가"를 계산으로 판단해야 합니다.

이 프로그램은 그 판단의 기본 계산인 **MAC(Multiply-Accumulate, 곱하고 더하기)** 을 파이썬 반복문으로 직접 구현했습니다. 패턴과 필터를 같은 위치끼리 곱해서 모두 더하면 둘이 얼마나 닮았는지를 나타내는 점수가 나오고, 점수가 큰 쪽으로 판정합니다.

- **모드 1**: 3×3 필터 2개(A, B)와 패턴을 직접 입력받아 판정합니다.
- **모드 2**: data.json의 패턴 6개를 한꺼번에 판정하고, 정답(expected)과 비교해 PASS/FAIL을 출력합니다.
- **성능 분석**: 3×3부터 25×25까지 크기별 MAC 시간을 10번씩 재서 평균을 냅니다.

data.json의 라벨이 `+`, `x`, `cross`처럼 제각각이라 표준 라벨 `Cross`, `X`로 **정규화**했고, 실수 계산 오차 때문에 점수는 **허용오차(epsilon) 1e-9**로 비교했습니다. 결과는 6개 중 3개 통과, 3개 실패입니다. 실패한 3개는 수학적으로 두 점수가 똑같은 케이스라 규칙대로 동점(UNDECIDED) 처리된 것이고, 로직 오류가 아닙니다. 자세한 분석은 결과 리포트에 정리했습니다.

## 2. 구현 요약

### 2-1. 데이터 구조: Matrix

패턴과 필터는 모두 N×N 숫자 표라서 `Matrix` 클래스 하나로 저장합니다. 내부는 2차원 리스트 `rows`이고, `get(r, c)`와 `set(r, c, value)`로 원하는 위치의 값을 읽고 씁니다.

`from_rows`는 리스트로 Matrix를 만들면서 정사각형인지, 모든 값이 숫자인지 검사합니다. True/False, NaN, Infinity도 막아서 잘못된 값이 계산까지 가지 않게 했습니다. 3×3, 5×5, 13×13, 25×25를 모두 같은 클래스로 처리합니다.

### 2-2. MAC 연산

MAC은 같은 위치끼리 곱하고(Multiply) 그 결과를 계속 더하는(Accumulate) 연산입니다. `mac.py`의 `mac()`은 NumPy 없이 이중 반복문으로 모든 칸의 `패턴 값 × 필터 값`을 `total`에 더합니다. 두 행렬의 크기가 다르면 계산하지 않고 오류를 냅니다.

```python
total = 0.0
for r in range(n):
    for c in range(n):
        total += p[r][c] * f[r][c]
return total
```

십자가 패턴에 십자가 필터를 곱하면 겹치는 5칸이 1×1이라 점수가 5이고, X 필터를 곱하면 가운데 1칸만 겹쳐서 점수가 1입니다. 겹치는 칸이 많을수록 점수가 커지므로, **점수는 필터와 얼마나 닮았는지를 나타내는 유사도**입니다.

```
입력(십자가)   십자가 필터            입력(십자가)   X 필터
0 1 0          0 1 0                  0 1 0          1 0 1
1 1 1    ×     1 1 1   →  점수 5      1 1 1    ×     0 1 0   →  점수 1
0 1 0          0 1 0                  0 1 0          1 0 1
```

실제 AI는 이런 곱하고 더하기를 이미지 한 장에 수억 번 합니다. 명령을 하나씩 순서대로 처리하는 CPU로는 벅차서, 수천 개의 MAC을 동시에 처리하는 NPU 같은 전용 칩을 사용합니다.

### 2-3. 모드 1 입력 검증

모드 1은 한 줄에 숫자 3개씩 공백으로 구분해 입력받습니다. `console.py`의 `parse_row()`가 한 줄을 입력할 때마다 바로 검사해서, 빈 줄은 행 수 불일치, 숫자가 3개가 아니면 열 수 불일치, 숫자로 바꿀 수 없으면 파싱 실패로 처리합니다.

이때 "입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요."라는 안내와 함께 **틀린 줄만** 다시 입력받습니다. nan, inf 같은 값도 거부합니다.

| 입력 예 | 결과 |
|---|---|
| `0 1 0/1 1 1/0 1 0` (한 줄에 이어 씀) | 열 수 불일치: 3개가 필요한데 7개입니다 |
| `a b c` | 숫자 파싱 실패: 'a' |
| 빈 줄 (Enter만) | 행 수 불일치: 빈 줄이 입력됐습니다 |
| 입력 중 Ctrl+C | 에러 메시지 없이 "프로그램을 종료합니다." |

### 2-4. 라벨 정규화와 키 규칙

data.json은 같은 뜻을 여러 모양으로 씁니다. 정답(expected)은 `+`와 `x`이고, 필터 키는 `cross`와 `x`입니다. 이걸 그대로 비교하면 판정 결과 `Cross`와 정답 `+`가 서로 다른 글자라서, 맞게 판정해도 FAIL이 됩니다.

그래서 `labels.py`의 `normalize_label()` **한 곳**에서 앞뒤 공백을 지우고 소문자로 바꾼 다음 표준 라벨로 바꿉니다. 해석할 수 없는 라벨은 `None`을 돌려줘서 그 케이스만 FAIL로 처리합니다. 화면 출력과 PASS/FAIL 비교는 모두 이 표준 라벨로 합니다.

```python
_ALIASES = {
    "+": CROSS,      # expected 값
    "cross": CROSS,  # filter 키, 'Cross'도 소문자로 바꾸면 여기에 걸린다
    "x": X,          # expected 값과 filter 키, 'X'도 포함
}


def normalize_label(raw):
    """'+', 'cross', ' Cross ' → 'Cross' / 'x', 'X' → 'X' / 해석할 수 없으면 None"""
    if not isinstance(raw, str):
        return None
    return _ALIASES.get(raw.strip().lower())
```

| 원래 표기 | 쓰이는 곳 | 표준 라벨 |
|---|---|---|
| `+` | expected | Cross |
| `cross` | filter 키 | Cross |
| `x` | expected, filter 키 | X |

키 규칙은 `size_{N}_{idx}`입니다. `loader.py`의 `size_from_key()`가 `size_13_2`를 `_`로 나눠 N=13을 꺼내고, 그 N으로 `size_13` 필터를 골라 계산합니다. 키 형식이 맞지 않으면 그 케이스만 FAIL로 처리합니다.

### 2-5. 동점 처리 정책 (epsilon)

컴퓨터는 0.1 같은 수를 2진수로 정확히 나타낼 수 없어서, 여러 번 더하면 아주 작은 오차가 쌓입니다. 실제로 0.1을 9번 더하면 0.9가 아니라 `0.8999999999999999`가 나옵니다.

그래서 두 점수를 `==`나 `>`로 바로 비교하지 않고, **두 점수 차이의 절댓값이 `EPSILON = 1e-9`보다 작으면 동점**으로 봅니다. 동점이면 모드 1은 "판정 불가", 모드 2는 `UNDECIDED`로 판정합니다.

```python
EPSILON = 1e-9  # 두 점수의 차이가 이 값보다 작으면 같은 점수(동점)로 본다.


def is_tie(score_a, score_b, epsilon=EPSILON):
    """부동소수점 오차를 고려해, 두 점수의 차이가 epsilon보다 작으면 동점으로 본다."""
    return abs(score_a - score_b) < epsilon
```

1e-9는 이 데이터의 계산 오차(1e-16~1e-15)보다는 수십만 배 이상 크고, 실제 점수 차이(이 데이터에서 가장 작은 것이 8.8)보다는 훨씬 작습니다. 그래서 오차와 진짜 차이를 확실하게 구분할 수 있습니다.

```
모드 1 동점 확인 (A = 0.1이 9칸, B = 0.9가 1칸, 패턴 = 전부 1)
A 점수: 0.8999999999999999
B 점수: 0.9
판정: 판정 불가 (|A-B| < 1e-09)
```

### 2-6. 스키마 검증과 실패 원인 분류

data.json은 두 단계로 검사합니다. 파일이 없거나, JSON 문법이 틀리거나, UTF-8이 아니거나, `filters`·`patterns` 항목이 없는 등 파일 전체에 문제가 있으면 `load_json()`이 안내 문구를 출력하고 메뉴로 돌아갑니다.

키 형식 오류, 크기 불일치, 숫자가 아닌 값, 해석할 수 없는 라벨처럼 항목 하나에 문제가 있으면 **프로그램을 멈추지 않고 그 케이스만 FAIL** 처리하고 이유를 남깁니다. 실패 이유는 원인에 따라 세 가지로 나눠 출력합니다.

| 분류 | 뜻 | 예 |
|---|---|---|
| 데이터/스키마 | 데이터 형식 자체가 틀림 | 키 형식 오류, 크기 불일치, 숫자 아닌 값, 라벨 해석 불가, 필터 없음 |
| 로직 | 데이터는 정상인데 판정이 expected와 다름 | 필터 선택·라벨 정규화·MAC 점검 필요 |
| 수치 비교 | 두 점수 차이가 epsilon보다 작아 UNDECIDED | 부동소수점 오차로 생긴 동점 |

### 2-7. 성능 측정 방법

`benchmark.py`의 `measure_ms()`는 MAC 함수를 부르는 구간만 `time.perf_counter`로 잽니다. 입력, 파일 읽기, 화면 출력은 측정 구간 밖에서 미리 끝냅니다. 재기 전에 0.05초 동안 같은 계산을 반복해서 CPU를 깨우는 워밍업을 하고, 그다음 10번 재서 평균을 ms로 냅니다. 워밍업이 없으면 CPU가 절전 상태에서 깨어나는 동안 잰 첫 측정값이 느리게 나옵니다.

```python
end = time.perf_counter() + WARMUP_SECONDS
while time.perf_counter() < end:  # 워밍업 (측정 제외)
    func(*args)
total = 0.0
for _ in range(repeat):
    start = time.perf_counter()
    func(*args)
    total += time.perf_counter() - start
return total / repeat * 1000  # 초 → 밀리초(ms)
```

크기별 측정에는 `generator.py`로 만든 N×N 십자가 패턴과 X 필터를 씁니다. 계산 시간은 값이 아니라 칸 수에만 달려 있어서, data.json에 없는 3×3까지 같은 조건으로 잴 수 있습니다. 생성기가 만든 패턴이 data.json의 입력 패턴 6개와 칸 하나까지 똑같다는 것도 확인했습니다.

### 3-2. FAIL 원인 분석

실패한 3개는 데이터 문제도, 로직 문제도 아닌 **수치 비교 문제**입니다.

첫째, 세 케이스 모두 **수학적으로는 두 점수가 정확히 같습니다.** size_5_1은 X 필터의 0.1이 9칸이라 0.1 × 9 = 0.9로 Cross 점수 0.9와 같고, size_13_2는 십자가 필터의 0.3이 25칸이라 0.3 × 25 = 7.5로 X 점수 7.5와 같고, size_25_1은 X 필터의 0.1이 49칸이라 0.1 × 49 = 4.9로 Cross 점수 4.9와 같습니다. 일부러 동점이 되도록 필터 가중치가 설계된 케이스입니다.

둘째, 0.1과 0.3은 2진수로 정확히 표현할 수 없어서, 여러 번 더하는 동안 작은 오차가 생겼습니다. 두 점수의 차이는 각각 1.11e-16, 2.66e-15, 1.78e-15입니다.

셋째, 이 차이는 epsilon(1e-9)보다 훨씬 작아서 동점, 즉 UNDECIDED로 판정했습니다. expected는 Cross나 X 중 하나이므로, 동점 처리 규칙에 따라 FAIL입니다.

넷째, 만약 epsilon 없이 `>`로만 비교했다면 세 케이스 모두 **expected와 반대 라벨**이 나옵니다. 오차가 하필 모두 정답 반대 방향으로 생겼기 때문입니다. 그랬다면 "MAC 로직이 틀렸다"고 잘못 진단했을 것입니다. epsilon 정책 덕분에 이것이 로직 오류가 아니라 수치 비교 문제라는 것을 분리할 수 있었습니다.

나머지 두 분류는 0개입니다. 라벨 정규화로 `+`, `x`, `cross` 표기 차이를 흡수했고(정규화 없이 비교하면 6개 모두 FAIL), 키에서 N을 꺼내 필터를 고르고 크기를 검증해서 데이터/스키마 문제가 없음을 확인했습니다. 점수 차이가 확실한 3개는 모두 정답이므로 MAC과 필터 선택 로직도 정상입니다.

| 케이스 | 수학적 값 | 실제 계산 (Cross / X) | 차이 | `>`만 쓴 판정 | epsilon 판정 | expected |
|---|---|---|---|---|---|---|
| size_5_1 | 0.9 = 0.1 × 9 | 0.9 / 0.8999999999999999 | 1.11e-16 | Cross | UNDECIDED | X |
| size_13_2 | 7.5 = 0.3 × 25 | 7.499999999999997 / 7.5 | 2.66e-15 | X | UNDECIDED | Cross |
| size_25_1 | 4.9 = 0.1 × 49 | 4.9 / 4.899999999999999 | 1.78e-15 | Cross | UNDECIDED | X |

실패가 생겼을 때는 아래 순서로 원인을 좁혔습니다.

1. 데이터/스키마: 키 형식, 크기, 숫자, 라벨이 정상인가? → 모두 정상으로 로드됨
2. 로직: 점수 차이가 확실한 케이스는 맞게 판정하는가? → PASS 3개 모두 정답
3. 수치 비교: 실패 케이스의 점수 차이가 epsilon보다 작은가? → 3개 모두 1e-15 이하 → 수치 비교 문제로 결론

### 3-3. 성능 분석과 O(N²)

노트북(WSL2)에서 크기별로 10회 평균을 낸 값입니다.

| 크기(N×N) | 연산 횟수(N²) | 평균 시간(ms) | 칸 1개당 시간 |
|---|---|---|---|
| 3×3 | 9 | 0.0006 | 약 67 ns |
| 5×5 | 25 | 0.0013 | 약 52 ns |
| 13×13 | 169 | 0.0053 | 약 31 ns |
| 25×25 | 625 | 0.0191 | 약 31 ns |

MAC은 N×N의 모든 칸에서 곱셈 1번, 덧셈 1번을 하므로 연산 횟수가 N²이고, 시간 복잡도는 **O(N²)** 입니다.

측정값도 이를 뒷받침합니다. 13×13에서 25×25로 가면 연산 횟수는 169에서 625로 3.7배, 시간은 0.0053ms에서 0.0191ms로 3.6배 늘어서 거의 비례합니다. 시간을 칸 수로 나눈 칸 1개당 시간도 13×13과 25×25에서 똑같이 약 31ns입니다. 칸 수가 늘어난 만큼 시간이 늘어난다는 뜻입니다.

3×3과 5×5는 칸당 시간이 더 커 보입니다. 함수를 부르고 반복문을 준비하는 고정 비용이 계산량과 상관없이 들어가는데, 칸이 적으면 이 고정 비용의 비중이 커지기 때문입니다. 측정값은 대략 `시간 ≈ 0.0002ms + N² × 0.00003ms`로 설명되고, N이 커질수록 N² 부분이 시간을 결정합니다.

정리하면 N이 2배가 되면 시간은 약 4배가 됩니다. 실제 AI처럼 필터가 수백×수백이고 그런 필터를 수천 개 쓰면 계산량이 매우 빠르게 커지기 때문에, 반복 연산을 한꺼번에 처리하는 NPU가 필요합니다.

측정 시간이 1ms보다 훨씬 짧아서 실행할 때마다 숫자가 조금씩 흔들립니다. 같은 25×25가 0.0138ms로 나온 적도, 0.0191ms로 나온 적도 있습니다. 그래서 한 번의 숫자보다 크기 사이의 비율과 경향으로 해석했습니다.

처음에는 워밍업을 1번만 해서 3×3이 0.0025ms로 5×5(0.0010ms)보다 느리게 나왔습니다. CPU가 절전 상태에서 깨어나는 동안 첫 크기를 쟀기 때문이라, 워밍업을 0.05초 동안 반복하도록 바꿨고, 그 뒤로는 위 표처럼 크기 순서대로 시간이 늘어납니다.
